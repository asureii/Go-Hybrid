- **Step that slowed the run most and defect / documentation gap found**:
  - **Gap 1 (`nitro_manage_template` missing `catalog_id`)**: The REST endpoint `POST /v1/my/templates` (`https://docs.nitrosend.com/api/operations/operation-v1-my-templates-post.md`) accepts `catalog_id` (string, e.g. `"welcome_note"`) to record gallery template provenance when saving a customized design, whereas the MCP tool `nitro_manage_template` (`https://docs.nitrosend.com/mcp/operations/operation-nitro-manage-template-tool.md`) only accepts `based_on` (integer, for an existing account template ID) and rejects string catalog slugs.
  - **Gap 2 (`nitro_send_message` dry-run vs live capacity check)**: Calling `nitro_send_message` with `dry_run: true` and `template_id: 27554` returned `valid: true` with no warnings, but immediately calling `nitro_send_message` with `dry_run: false` failed with `error_code: "signup_sending_capacity_reached"` (`shared_abuse_capacity`), whereas `nitro_send_test_message` for the same `template_id: 27554` succeeded immediately and emitted the receipt.
- **One change we would make**:
  - Add an optional `catalog_id` string parameter (or allow `based_on` to accept a public catalog slug like `"welcome_note"`) in `nitro_manage_template` so MCP agents can clone and customize public gallery templates directly over MCP without calling `POST /v1/my/templates` over REST.
